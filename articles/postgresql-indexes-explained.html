PostgreSQL Indexes Explained: When B-tree Helps, When It Hurts

Adding indexes in a panic can make writes several times slower. Ship only the indexes backed by EXPLAIN ANALYZE and a note about the workload they serve.

RM
By Ram
Published August 29, 2026 • Updated October 9, 2026 • 4 min read • ~1001 words

What you will learn

  • Indexes speed reads and tax writes — prove the trade with EXPLAIN ANALYZE.
  • Composite column order should follow equality filters then range or sort.
  • Partial and expression indexes beat scattershot single-column indexes.
  • Use CREATE INDEX CONCURRENTLY in production.
  • Audit idx_scan and remove indexes that never earn their keep.
  • Index foreign key columns so deletes and joins do not seq-scan children.

What a B-tree index is paying for

A B-tree index is a sorted structure Postgres maintains beside the heap table. Point lookups and range scans on the indexed columns become logarithmic instead of sequential. The cost: every INSERT, UPDATE, and DELETE must update matching indexes. Indexing six columns of a busy events table “just in case” can multiply insert latency.

Low-cardinality columns such as is_active boolean alone rarely deserve a standalone B-tree. Postgres may still seq-scan if half the rows match. Composite or partial indexes are usually smarter.

Keep a list of candidate indexes with the query from APM, current p95, estimated rows, the proposed definition, and the write-path impact. If you cannot fill those cells, do not create the index yet.

EXPLAIN ANALYZE before and after

Never argue about indexes without plans. EXPLAIN (ANALYZE, BUFFERS) on a production-sized copy or anonymized dump shows actual time and whether an Index Scan or Bitmap Index Scan appeared.

Watch for Seq Scan on multi-million-row tables with a selective WHERE, and for Index Scan that still filters most rows because the index does not match the predicate well. Also compare shared hit versus read buffers — an index that lives in RAM behaves differently under cold cache.

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE customer_id = 48291
  AND created_at >= NOW() - INTERVAL '30 days'
ORDER BY created_at DESC
LIMIT 50;

Composite order matters

For the query above, customer_id then created_at DESC matches equality then sort or range. created_at then customer_id is weaker for that filter pattern. The leftmost-prefix rule familiar from MySQL still applies to the default B-tree.

Build that index with CREATE INDEX CONCURRENTLY on orders (customer_id, created_at DESC). On a multi-million-row table, a query like this typically drops from a sequential scan taking hundreds of milliseconds to an index scan taking a few. CONCURRENTLY matters because a plain CREATE INDEX blocks writes to the table for the whole build.

INCLUDE columns can help a report query avoid heap fetches: include status and total_cents so an index-only scan answers the list view. Check heap fetches in EXPLAIN before celebrating.

-- Prefer concurrent builds in production
CREATE INDEX CONCURRENTLY idx_orders_customer_created
  ON orders (customer_id, created_at DESC);

-- Partial index: only open tickets (smaller, faster)
CREATE INDEX CONCURRENTLY idx_tickets_open_assignee
  ON tickets (assignee_id)
  WHERE status = 'open';

When indexes hurt

Write-heavy tables with indexes unused by queries are pure overhead. Functions wrapping columns such as LOWER(email) cannot use a plain email index unless you create an expression index on LOWER(email). Leading wildcards in LIKE will not use a normal B-tree; consider pg_trgm when search needs it.

Too many overlapping indexes confuse the planner and waste cache. Audit pg_stat_user_indexes for idx_scan = 0 after a meaningful period of weeks, not hours.

On write-heavy tables, dropping indexes that no query uses often improves insert latency more than any read path suffers, and frees significant disk.

  • Measure with EXPLAIN ANALYZE on realistic data volumes
  • Match composite column order to filter plus sort patterns
  • Prefer partial indexes for common status filters
  • Build CONCURRENTLY in prod to avoid long write locks
  • Drop unused indexes after watching idx_scan

Finding dead indexes in production

After a couple of weeks of real traffic, query pg_stat_user_indexes together with pg_relation_size. Anything with zero scans and non-trivial size goes on a drop-candidate list. Exclude brand-new indexes and unique constraints that enforce correctness even if rarely used for reads.

Drop one at a time during low traffic, watch APM for a week, then continue. Never bulk-drop six indexes before a holiday weekend.

SELECT
  schemaname || '.' || relname AS table,
  indexrelname AS index,
  idx_scan,
  pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 20;

Unique constraints are indexes too

A UNIQUE constraint creates a unique B-tree. Do not also add a redundant non-unique index on the same columns—migrations that create both pay double write cost for no gain.

Partial unique indexes are excellent for soft-delete: unique on email where deleted_at is null lets you reuse emails after delete without complicated application checks, and removes the race conditions of app-level uniqueness checks.

CREATE UNIQUE INDEX CONCURRENTLY idx_users_email_active
  ON users (email)
  WHERE deleted_at IS NULL;

Maintenance to schedule

Autovacuum usually keeps things healthy; bloated indexes after bulk deletes sometimes need REINDEX CONCURRENTLY. Alert when table bloat estimates cross a threshold rather than reindexing on a fixed calendar.

Foreign keys deserve indexes on the referencing column — not only for reads, but so ON DELETE cascades do not seq-scan child tables. A missing FK index can turn deleting one parent row into a multi-second operation.

Staging with production-shaped data

Plans flip with scale. On 50k rows almost everything looks fine. On 20M rows the planner chooses differently. Refresh a sanitized staging database from production regularly for index experiments, with PII scrubbed.

Run EXPLAIN ANALYZE at least three times and discard the coldest run when comparing. Then test under a light write load, because an index that helps a read-only session can still hurt the API when inserts contend on the same pages. Uniform random foreign keys produce unrealistically perfect indexes; real customers cluster.

Monitoring after ship

After creating an index, watch query p95 from APM, insert and update p95 on the table, index size growth, and vacuum activity. A week of green metrics earns a note in the runbook; a write regression earns a revert even if the read looks prettier.

Also check whether the planner actually uses the new index. An index that never gets selected is pure cost. Sometimes statistics are stale — running ANALYZE on the table after a bulk import often fixes a stubborn seq scan.

A small decision framework

Slow query in APM, capture SQL, run EXPLAIN ANALYZE, if seq scan on large table and selective filter then design minimal index, create concurrently on staging, compare plans and write p95, then ship. If the filter returns more than 20 to 30 percent of the table, rethink; a seq scan may already be optimal.

Ship the smallest index that changes the plan. You can always add INCLUDE columns later; removing a wide unused index under write load is harder socially than technically.
